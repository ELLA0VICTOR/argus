  **[Medium] CR-INIT-1 — A third party can block vault initialization by pre-creating its ATA.** Location: `programs/argus/src/instructions/initialize_vault.rs:34`; missing regression near `programs/argus/tests/initialize_vault.rs:309`. The vault address and canonical ATA are predictable from public creator/id/mint. Anyone can pay to create that ATA without the creator or vault authority signing, before the Vault account exists. The ATA uses plain `init`: Anchor 1.2.2 always calls the non-idempotent associated-token create instruction, so the later legitimate initialization fails on the already-existing ATA. Repeating the same vault ID cannot recover; an attacker can also front-run another announced ID. Impact is creation denial of service, not an INV-1 funds escape. Suggested fix: make ONLY the ATA creation idempotent (`init_if_needed` with the required Anchor feature and existing mint/authority/program/address checks, or explicit `create_idempotent` after validation). Keep the Vault itself on `init`, preserving duplicate-init rejection. Test: an unrelated funded payer creates ATA(vault PDA, mint) first; creator initialization then succeeds, preserves any pre-funded token balance, and does not require the attacker. Also retain wrong-ATA/mint/authority/program rejection and same-Vault-ID reinitialization failure. Evidence: [Anchor 1.2.2 ATA init generator](https://github.com/solana-foundation/anchor/blob/v1.2.2/lang/syn/src/codegen/accounts/constraints.rs#L748), [non-idempotent versus idempotent CPI helpers](https://github.com/solana-foundation/anchor/blob/v1.2.2/spl/src/associated_token.rs#L12).

  **[Low] CR-INIT-2 — The mixed mint/program rejection does not guarantee the promised UnsupportedMint code.** Locations: `programs/argus/src/instructions/initialize_vault.rs:27`, `programs/argus/src/instructions/initialize_vault.rs:34`, `programs/argus/tests/initialize_vault.rs:278`. With a Token-2022 mint but the classic token program, ATA initialization can fail in the token CPI before the custom mint-owner check runs. The test currently accepts any error, so it does not establish the spec/error-mapping contract for this case. Token-2022 is still rejected; this is an error-reporting/test-contract issue, not a role or funds bypass. Suggested fix: validate classic mint/program ownership before explicitly creating the ATA, or explicitly document which malformed account combinations may return framework/SPL errors. Merely moving the mint field earlier does not change Anchor init ordering. Test: strengthen the mixed case to assert UnsupportedMint (6025) if that contract is intended, add classic-mint/Token-2022-program substitution, and assert failed initialization leaves no new Vault/ATA state. This error precedence is source-derived; confirm it with the compiled program. Evidence: [Anchor 1.2.2 init-before-access constraint generation](https://github.com/solana-foundation/anchor/blob/v1.2.2/lang/syn/src/codegen/accounts/try_accounts.rs#L274).
